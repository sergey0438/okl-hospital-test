# OKL Hospital — тестова версія (робочий прототип)

КНП ХОР «ОКЛ» — Облік військовослужбовців. Повністю робочий фронтенд-прототип
нового інтерфейсу з реальним CRUD. Дані зберігаються локально в браузері
(localStorage), тому все працює **без сервера** — зручно тестувати перед
підключенням до бойового бекенду.

---

## Як запустити

Варіант 1 (найпростіший): відкрийте `index.html` подвійним кліком у браузері
(Chrome / Safari / Edge).

Варіант 2 (рекомендовано, ближче до бойового): підніміть локальний сервер у
теці проєкту:

```bash
python3 -m http.server 8000
# відкрийте http://localhost:8000
```

Вхід: оберіть роль, введіть **будь-яке прізвище та будь-який пароль** — у
тестовій версії авторизація не перевіряється на сервері (див. розділ
«Безпека» нижче).

---

## Що працює

- **Пацієнти:** додавання (Військовий / Цивільний з різними категоріями),
  редагування, перегляд картки, виписка (7 типів, «Помер» → час смерті),
  видалення з підтвердженням. Пошук, фільтри (категорія / відділення / стан),
  пагінація. KPI-картки рахуються з реальних даних.
- **Операції за добу:** редаговані поля, підсумки, збереження.
- **Звіт 08:00:** дві вкладки (Військові / Усі), «Внести вільні ліжка» (drawer)
  зі збереженням.
- **Журнал за добу:** автозаповнення стовпців *Перебуває / Лежачіх / Військові /
  Вибухові* з реєстру «Пацієнти», ручні поля руху за добу, автосума.
- **Статистика:** розподіл за категоріями, Військові/Цивільні, статистика
  виписок — **усе рахується з реальних дій** (випишіть пацієнта — графік
  оновиться).
- **Налаштування:** захищена зона (будь-який пароль), статуси, аудит-лог,
  очищення бази (відновлює демо-дані).
- Сповіщення (дзвіночок), мобільне меню «Ще», тости, порожні стани, підтвердження.

Усі зміни **зберігаються між перезавантаженнями** сторінки.

## Скидання даних

- У додатку: «Налаштування» → пароль → **Очищення бази** → ввести `ОЧИСТИТИ`.
- Або вручну: у консолі браузера `localStorage.removeItem('okl_db_v1')` і оновити.

## Структура

```
index.html            — розмітка (усі сторінки й модалки)
assets/styles.css     — дизайн-система (design tokens, компоненти, адаптив)
assets/store.js       — шар даних (localStorage). Тут точки заміни на API.
assets/app.js         — уся логіка інтерфейсу та CRUD
assets/store.firebase.example.js — приклад, як підключити бойовий бекенд
```

---

## Перехід на бойову версію (Firebase / Cloud Functions)

Уся робота з даними ізольована в `assets/store.js`. Щоб під'єднати ваш
існуючий API `europe-west1-okl-hospital-41197`, замініть тіла методів
`DB.patients / addPatient / updatePatient / removePatient / getKV / setKV`
на `fetch()`-виклики до ваших ендпоінтів (позначено `// TODO(API)`).
`app.js` при цьому **не змінюється**. Приклад — у
`assets/store.firebase.example.js`.

Порядок публікації в основну версію:
1. Підключити `store.js` до реального API (замість localStorage).
2. Замінити екран входу на **Firebase Authentication** (індивідуальні акаунти,
   роль через custom claims) — замість спільного пароля на роль.
3. `firebase deploy` (фронтенд уже на Firebase Hosting).

## Безпека (важливо)

Це **тестовий фронтенд**. Він НЕ є засобом безпеки:

- вхід не перевіряється на сервері;
- дані лежать локально у браузері.

Реальна безпека даних вирішується **на сервері (Cloud Functions)**:
перевірка токена й ролі на кожному ендпоінті, індивідуальні акаунти замість
спільних паролів, rate-limit, аудит-лог, м'яке видалення, мінімізація доступу.
База містить чутливі дані (статус «з полону», категорії, діагнози
військових) — серверну перевірку ролі варто зробити пріоритетом №1.
